# DARAI — план разработки

Статус: проектирование, исходного кода приложения ещё нет. Горизонт MVP — 5 часов активной разработки при подготовленных моделях и подходящем оборудовании. Загрузка весов, доступ к gated-моделям и нехватка вычислительных ресурсов могут увеличить срок. Не обещаем весь объём до проверки оборудования.

## 1. Продукт и границы MVP

Делаем внутреннюю CRM совещаний: сотрудники, голосовые профили, встречи, протоколы, поручения и центр уведомлений. Встреча создаётся в CRM до загрузки записи: название, дата, часовой пояс, участники, секретарь/организатор и повестка. Собственный сервис видеозвонков для MVP не нужен — запись загружается в карточку встречи.

Основной путь:

1. Администратор создаёт сотрудника: ФИО, должность, департамент; при необходимости выдаёт локальную учётную запись.
2. Сотрудник с уведомлением о назначении записи регистрирует голос: ориентир 20–30 секунд чистой одиночной речи, без музыки. Длительность уточняется проверкой качества.
3. Секретарь создаёт встречу, выбирает участников. Приглашения появляются в их центре уведомлений.
4. Секретарь загружает запись; CRM показывает этап и ошибку, если обработка не удалась.
5. После локальной обработки секретарь слушает спорные фрагменты, подтверждает личности, исправляет поручения и саммари.
6. Утверждение протокола публикует поручения исполнителям; DOCX/PDF доступен из встречи.
7. Исполнитель видит «Мои поручения», отмечает выполнение. Напоминания о сроках появляются внутри CRM.

**В MVP:** локальный вход, справочник сотрудников, регистрация голоса, создание встреч, загрузка файла, весь AI-пайплайн, ручная проверка, экспорт, список задач, внутренние уведомления с polling.

**После MVP:** захват live-аудио, WebSocket, боты Teams/Zoom/Meet, внешние рассылки, СЭД, расширенная аналитика, корпоративный SSO, промышленная очередь. Доступность записи системного звука в браузере проверяется отдельно для выбранной ОС; getDisplayMedia не заменяет интеграцию с платформой встречи.

## 3. Модель данных

| Сущность | Основные поля |
| --- | --- |
| Employee | id, fio, position, department, active |
| User | id, employee_id, login, password_hash, role: admin/secretary/employee |
| VoiceProfile | employee_id, vector, model_id, model_revision, dimension, created_at, consent_at, quality_status |
| Meeting | id, title, agenda, starts_at, timezone, organizer_id, secretary_id, approval_status: draft/confirmed |
| MeetingParticipant | meeting_id, employee_id; уникальная пара |
| Recording | id, meeting_id, local_path, processing_status: processing/done/error, stage, error_code, generation |
| Speaker | meeting_id, recording_id, label, proposed_employee_id, confirmed_employee_id, similarity, review_required |
| Utterance | recording_id, start, end, speaker_label, text, uncertain |
| Task | id, meeting_id, from_ref, to_employee_id, task, deadline, evidence, source_utterance_ids, confidence, status: draft/confirmed, execution_status: in_progress/completed |
| Notification | id, recipient_user_id, event_type, meeting_id/task_id, created_at, read_at, dedup_key |

Employee — участник, User — доступ в систему: сотрудник без аккаунта может участвовать и распознаваться, но не получает персональное уведомление до создания аккаунта. VoiceProfile хранится отдельно и не выдаётся через обычный API сотрудников. Размерность pgvector определяется фактическим выходом зафиксированной модели.

Просрочка вычисляется из срока, часового пояса встречи и execution_status, не хранится как конкурирующий статус. Если задана только дата, срок истекает в конце этого дня в часовом поясе встречи. Время событий хранить в UTC. Подтверждённый протокол имеет версию; экспорт использует сохранённые правки, а не новый ответ LLM.

## 4. API

Все перечисленные маршруты — планируемый контракт, пока не реализованы. Все защищённые маршруты проверяют сессию и доступ к сущности.

| Метод и путь | Контракт |
| --- | --- |
| POST /auth/login | login/password → сессия в HttpOnly cookie |
| POST /auth/logout | Завершить сессию |
| GET /auth/me | Текущий пользователь и роль |
| POST /users | Администратор создаёт аккаунт для employee_id, роль и пароль |
| GET /employees | Список и поиск сотрудников, без векторов |
| POST /employees | `{fio, position, department}` |
| PATCH /employees/{id} | Исправить карточку |
| POST /employees/{id}/voice | multipart wav + подтверждение уведомления → регистрация профиля, статус качества |
| DELETE /employees/{id}/voice | Удалить голосовой профиль и связанные регистрационные образцы |
| GET /meetings | Доступные пользователю встречи |
| POST /meetings | Основной вариант: JSON `{title, starts_at, timezone, agenda, participant_ids}` → встреча без записи |
| POST /meetings | Совместимый быстрый вариант: multipart audio + participant_ids[] + title/starts_at/timezone → встреча и обработка |
| POST /meetings/{id}/recordings | multipart audio → 202, recording_id, processing_status |
| POST /meetings/{id}/recordings/{recording_id}/retry | Повтор после ошибки, без дублирования результатов |
| GET /meetings/{id} | Метаданные, участники, статус/этап, транскрипт, спикеры, поручения, саммари, ошибки извлечения |
| PATCH /meetings/{id}/speakers | `{"SPEAKER_00": "employee_id"}`; null снимает привязку |
| PATCH /meetings/{id}/summary | `{summary}`; правки секретаря |
| PATCH /tasks/{id} | Секретарь правит поля поручения; исполнитель — только execution_status своей задачи |
| POST /meetings/{id}/confirm | Атомарно подтвердить текущую версию протокола и создать уведомления |
| GET /tasks?assignee=me | Мои поручения, фильтры |
| GET /notifications | Только уведомления текущего пользователя |
| PATCH /notifications/{id} | `{read: true}` |
| GET /meetings/{id}/export?fmt=docx\|pdf | Подтверждённый документ либо явно помеченный черновик |

Расширение исходного POST /meetings необходимо, чтобы встреча существовала до записи. Два варианта различаются по Content-Type и должны быть описаны в OpenAPI. На MVP у встречи одна активная запись; повторный запуск отклоняется при processing, замена после подтверждения запрещена до появления версионирования редактирования. SPEAKER_XX уникален в рамках активной записи, не во всей системе.

Исходные поля поручения сохраняются:

```json
{
  "id": "task-id",
  "from": "employee-id-or-SPEAKER_00",
  "to": null,
  "task": "Подготовить отчёт",
  "deadline": null,
  "evidence": "Подготовьте отчёт, ответственного определим позже",
  "confidence": 0.6,
  "status": "draft"
}
```

`from` — автор поручения, `to` — исполнитель. В JSON неизвестные значения — настоящий null, не строка "null". Дополнительные поля: source_utterance_ids, deadline_source, needs_review, execution_status. Confidence LLM не считать откалиброванной вероятностью. Подтверждение с неизвестным исполнителем/сроком требует явной отметки секретаря; без исполнителя персональное уведомление не создаётся, без срока напоминание не планируется.

## 5. Голос и извлечение поручений

- Enrollment и matching используют одну модель, revision и предобработку. Несовместимый профиль требует перерегистрации.
- Отбрасываем тишину, слишком короткие и перекрывающиеся интервалы; при отсутствии чистой речи оставляем «Неизвестный», а не вычисляем вектор из шума.
- Начальные значения env: VOICE_MIN_SEGMENT_SECONDS=1.5, VOICE_MATCH_THRESHOLD=0.55, VOICE_MATCH_MARGIN=0.08. Проверяем известного, незарегистрированного и двух похожих кандидатов.
- Венгерское назначение применяется с возможностью отказа. Оно не должно принудительно распознавать всех приглашённых: приглашённый мог не говорить. Ошибочное разбиение одного человека на несколько кластеров исправляется секретарём.
- При ручной смене спикера обновляются ссылки на автора поручения; исполнитель автоматически не заменяется — он определяется содержанием. Уже подтверждённые результаты не переписывать молча.
- ASR: task=transcribe, language=None, word_timestamps=True. Автоопределение языка не равно надёжному распознаванию переключений; отдельная смешанная фикстура обязательна.
- LLM: участники, дата, часовой пояс, ID реплик, контекст минимум ±3 реплики; для длинных встреч перекрывающиеся окна, дедупликация по evidence и источнику. Саммари охватывает всю встречу.
- Проверять ID исполнителя по участникам, реальность evidence в транскрипте, формат дат. Инструкции внутри транскрипта считать данными, не командами модели.
- Один повтор невалидного JSON; после второго сбоя возвращать extraction_error и пустые поручения. UI отличает ошибку от «поручений нет».

## 6. Уведомления внутри CRM

| Событие | Получатель | Когда |
| --- | --- | --- |
| Приглашение | Участники с аккаунтами | После создания встречи |
| Протокол готов к проверке / ошибка | Секретарь | После обработки |
| Поручение назначено | Исполнитель | После подтверждения протокола |
| Скоро срок | Исполнитель и организатор/куратор | За 24 часа, значение из env |
| Просрочка | Исполнитель и организатор/куратор | После истечения срока, если не выполнено |

На MVP — таблица Notification, polling UI и один периодический цикл backend, например раз в минуту. Запись уведомлений и утверждение протокола — транзакционно; уникальный dedup_key включает получателя, тип события, объект и версию срока. Повторный confirm/тик не создаёт дубли. После рестарта выполняется поиск пропущенных событий; завершённые и draft-задачи исключаются. Напоминания не требуют открытой вкладки браузера, но требуют работающего backend. При нескольких процессах нужен отдельный планировщик; MVP использует один.

## 7. Этапы на 5 часов

Бюджет ниже — ориентир для подготовленной среды, не гарантия. Каждый этап заканчивается проверяемым результатом. Если этап 0 не пройден, срок нужно пересчитать, а не скрывать проблему заглушками.

| Время | Этап | Результат и проверка |
| --- | --- | --- |
| 00:00–00:25 | 0. Проверка оборудования и моделей | Зафиксированы ОС/RAM/GPU, веса доступны локально; ASR, диаризация, embedding и LLM проходят короткий smoke-test без сети |
| 00:25–01:05 | 1. Каркас и CRM | Compose, миграции, auth, Employee/User/Meeting; из UI можно войти, создать сотрудника и встречу; доступ к чужой встрече запрещён |
| 01:05–02:00 | 2. Аудио и голос | Enrollment, загрузка, FFmpeg, ASR, diarization, align, matching; настоящая запись даёт реплики и кандидатов; неизвестный не назначается принудительно |
| 02:00–02:40 | 3. Поручения и саммари | Локальная LLM, схема Pydantic, retry, evidence; fixture проверяет автора, адресата, дату и неизвестные поля |
| 02:40–03:30 | 4. Проверка в UI | Транскрипт, аудио, спикеры, редактор задач/саммари, утверждение; ручная правка сохраняется после обновления страницы |
| 03:30–04:10 | 5. Экспорт и уведомления | DOCX/PDF с RU/KZ, мои задачи, назначения, сроки; повторный confirm не дублирует уведомления |
| 04:10–05:00 | 6. Полный прогон и документация | RU/KZ/mixed, неизвестный спикер, ошибки, offline, рестарт; README запуска, ограничения, результаты, демо |

Первый технический рубеж — реальный аудиофайл → локальные модели → структурированный JSON. Оформление интерфейса не должно откладывать проверку этого пути. Если времени не хватает, откладываем live, внешние интеграции, аналитику и визуальную полировку; незавершённые обязательные функции явно отмечаем.

## 8. Инфраструктура и ограничения MVP

Compose: frontend, backend, PostgreSQL/pgvector и один выбранный локальный LLM runtime. Модели подключены read-only, записи/экспорты и БД — отдельные volumes. Шрифты с казахскими символами включены в образ. LLM_MODEL и LLM_BASE_URL обязательны; выбор модели и размера зависит от оборудования и проверки казахского языка.

До разработки подтвердить: устройство запуска, наличие весов и доступа к pyannote, совместимые torch/torchaudio/pyannote/CTranslate2, память при одновременной загрузке, поддержку выбранного CPU/GPU в контейнерах. При нехватке памяти использовать отдельный self-hosted сервер внутри контура либо явно пересогласовать модель; не переключаться незаметно на облако.

BackgroundTasks подходит только для ограниченного MVP: один backend worker, ограничение конкуренции тяжёлых задач, операции модели не блокируют event loop. Прерванное задание после рестарта получает error и кнопку повтора. Запись результатов — атомарно по generation, чтобы не смешать попытки. Дальнейший этап — долговечная очередь и отдельный worker.

Безопасность MVP: локальная аутентификация, хеши паролей, серверные проверки ролей и участия, защита cookie/CSRF, лимиты загрузки и длительности, таймауты FFmpeg/LLM/LibreOffice, безопасные временные пути и изолированные каталоги конвертации, логи без содержания. Не публиковать БД и LLM наружу. В демонстрации — разрешённые обезличенные записи. Для реальной эксплуатации отдельно завершить TLS, шифрование хранилищ, аудит, резервное копирование и политику удаления.

## 9. Приёмка и демонстрация

- [ ] Подготовленная система запускается `docker compose up`, без скачиваний в runtime.
- [ ] Созданы три сотрудника и аккаунты; у двух есть голосовые профили, третий проверяет сценарий неизвестного голоса.
- [ ] Встреча создана внутри CRM, приглашения видны правильным пользователям.
- [ ] Короткие записи RU, KZ и mixed обработаны настоящими моделями; фикстуры регистрации отличаются от тестовых записей.
- [ ] Автор поручения и исполнитель не перепутаны; неназванный срок не выдуман.
- [ ] Неизвестный голос, overlap и неоднозначный адресат требуют проверки.
- [ ] Секретарь исправляет спикера/задачу/саммари; экспорт содержит эти правки.
- [ ] DOCX и PDF открываются, казахские символы читаются.
- [ ] Только подтверждённые задачи видны исполнителю; изменение статуса сохраняется.
- [ ] Напоминания проверены управляемыми часами/датами, повторный тик не создаёт дублей.
- [ ] Ошибка LLM, пустое аудио и рестарт не выглядят как успешный протокол.
- [ ] Чужие встречи/уведомления/голосовые профили недоступны при подстановке ID.
- [ ] При запрещённом внешнем egress весь путь работает; сетевой контроль не выявляет отправку данных/телеметрию.
- [ ] README содержит точные версии, оборудование, подготовку, команды, время обработки и известные ограничения.

Демонстрация: создать встречу → показать приглашение → загрузить короткую mixed-запись → открыть транскрипт и идентификацию → исправить одну неопределённость → подтвердить → открыть задачу и уведомление под исполнителем → скачать документ. RU/KZ результаты показать отдельно. Записать измеренное время и ошибки, не заявлять качество по одному удачному примеру.

## 10. После хакатона

1. Калибровка идентификации на разных микрофонах, языках и незарегистрированных голосах; измерение ложных совпадений и отказов.
2. Долговечная очередь, возобновление обработки, несколько записей, версии протоколов и согласование изменений.
3. Live-запись: MediaRecorder → упорядоченные чанки → сохранение контейнера → FFmpeg; разрыв/повтор, stop/finalize, согласование таймкодов. Диаризацию и matching финализировать на целой записи.
4. Планирование повторяющихся встреч, календарь, переносы, кураторы, эскалации и настройки уведомлений.
5. Интеграции платформ встреч/СЭД после проверки ограничений передачи данных.
6. Подготовка к промышленной эксплуатации: SSO, аудит, шифрование, retention, резервные копии, нагрузочное тестирование.

## Технические основания

- [faster-whisper](https://github.com/SYSTRAN/faster-whisper): word timestamps, локальные модели и требования вычислительного окружения.
- [pyannote speaker-diarization-3.1](https://huggingface.co/pyannote/speaker-diarization-3.1): вход 16 kHz mono и предварительное принятие условий доступа также к segmentation-3.0.
- [pyannote WeSpeaker](https://huggingface.co/pyannote/wespeaker-voxceleb-resnet34-LM): выбранная модель голосовых эмбеддингов.
- [FastAPI BackgroundTasks](https://fastapi.tiangolo.com/tutorial/background-tasks/): механизм фоновых задач; документация рекомендует отдельные инструменты для тяжёлых распределённых вычислений.
