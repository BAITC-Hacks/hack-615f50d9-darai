# DARAI — frontend

Реализован React + Vite + TypeScript интерфейс по `docs/API_CONTRACT.md` v1.1.0. Production всегда обращается к настоящему API. Фикстуры существуют только в `frontend/tests/e2e/` и подключаются перехватом запросов Playwright; переключателя «демо-успех» в приложении нет.

## Запуск

Подготовка с доступом к реестру пакетов (Node.js 22.12+ или поддерживаемый более новый Node):

```bash
cd frontend
npm ci
npm run dev -- --port 5173
```

Открыть `http://localhost:5173`. Backend по умолчанию должен отвечать на `http://127.0.0.1:8000`. Учётную запись создаёт backend; frontend не содержит встроенного логина или пароля.

Другой адрес **внутри контура** задаётся переменной процесса Vite, без изменения корневого `.env.example`:

```bash
BACKEND_URL=http://127.0.0.1:8001 npm run dev -- --port 5173
```

Браузер во всех случаях обращается к `/api`. `BACKEND_URL` не встраивается в JS приложения. Vite удаляет префикс `/api` и сохраняет исходный Host для same-origin/CSRF. `npm run preview` предназначен только для просмотра собранной статики: API-прокси production обеспечивает nginx, а не preview.

## Production и закрытый контур

Из корня репозитория на этапе подготовки:

```bash
docker build -t darai-frontend:local frontend
```

`frontend/Dockerfile`: сборка в Node 22 Alpine → только `dist/` и конфигурация в nginx 1.28 Alpine. Образ обслуживает порт **80**. Для Compose backend-агенту нужны `build.context: ./frontend`, общий network с сервисом `backend`, маршрутизация на `backend:8000` и публикация выбранного порта frontend. Корневой Compose frontend-агентом не менялся.

- `location /api/` → `http://backend:8000/`: завершающий `/` удаляет префикс.
- Остальные маршруты используют SPA fallback на `index.html`; API-ошибки не заменяются HTML приложения.
- Потоковая передача файла через прокси без полного буферизования; лимит nginx **1024 MiB**, таймауты загрузки/прокси **600 секунд**. Backend дополнительно проверяет собственные лимиты. Если `MAX_UPLOAD_MB` выше 1024, согласованно поднять лимит в `frontend/nginx.conf`.
- Клиент показывает прогресс XHR, отдельно ожидание проверки файла сервером, ошибки 413/422/503/сети/таймаута. Обычные JSON-запросы ограничены 45 секундами; загрузки — 600 секундами.
- `index.html` и API имеют `Cache-Control: no-store`; нет service worker и клиентского дискового кеша данных CRM.
- Access log nginx отключён, ошибки API-прокси не пишутся в error log: поисковые строки могут содержать персональные данные.
- Нет внешних API, CDN, web fonts, аналитики и телеметрии. Используются шрифты операционной системы с кириллицей/казахскими символами. Никакой загрузки пакетов при старте production-контейнера.
- Образы, npm-пакеты и Chromium для тестов загружаются **на подготовительном этапе**. Для изолированной машины заранее перенести готовый образ через `docker save` / `docker load`; не запускать сборку с ожиданием доступа к npm в закрытом контуре.

## Подключение API и состояние

Типы — `frontend/src/types.ts`; HTTP/CSRF, загрузки и экспорт — `frontend/src/api.ts`. Форматы сверены с контрактом и появившимися `backend/app/schemas.py` / `serializers.py` (чтение без изменений backend).

- `credentials: include`, серверная HttpOnly cookie-сессия. CSRF хранится только в памяти и восстанавливается из `GET /auth/me`; изменяющие запросы передают `X-CSRF-Token`.
- 401 очищает состояние текущего пользователя и показывает вход. Ошибочный пароль отображается в форме. HTML вместо JSON трактуется как ошибка подключения/прокси.
- Персональные данные и токены не записываются в `localStorage` или `sessionStorage`.
- API сохраняет сотрудников, встречи, голосовые профили, правки спикеров/саммари/поручений, выполнение и прочтение уведомлений. После обновления страницы данные запрашиваются заново.
- Видимость по роли — только удобство интерфейса. Проверки ролей, доступа по ID, приглашений, экспорта, аудио и CSRF обязан выполнять backend.
- Статус активной обработки запрашивается через маршрут recording каждые 3 секунды до `done`/`error`. Счётчик уведомлений и открытый центр уведомлений обновляются каждые 30 секунд. Каждый polling-цикл ставит следующий `setTimeout` после завершения предыдущего запроса; уход со страницы отменяет запрос и таймер. У счётчика и центра отдельные ограниченные циклы.
- Редактор встречи не опрашивает весь черновик во время ручных правок. Сохранение одного раздела не сбрасывает несохранённые поля другого.
- Несохранённые правки блокируют утверждение, экспорт, замену и повтор обработки записи; показано предупреждение, при закрытии/перезагрузке вкладки используется `beforeunload`. Переход по внутренней ссылке не открывает отдельный диалог: сначала сохранить или отменить правки.
- Подтверждение передаёт `draft_revision` и явное `acknowledge_incomplete`. При конфликте версия не утверждается; доступна загрузка актуального протокола для повторной проверки.

## Экраны

| Маршрут | Возможности |
| --- | --- |
| Экран входа при отсутствии сессии | Локальный логин/пароль, ошибки, текущий пользователь, выход |
| `/employees` | Серверный поиск по ФИО/должности/департаменту, пагинация, статус аккаунта и голоса |
| `/employees/new`, `/employees/:id` | Создание/правка ФИО, должности, департамента администратором; просмотр сотрудниками |
| Карточка сотрудника | Уведомление и согласие; MediaRecorder или файл `file` + `consent=true`; качество/несовместимость; перерегистрация и подтверждаемое удаление |
| `/meetings` | Поиск, пагинация, отдельные статусы обработки и утверждения |
| `/meetings/new` | Название, дата/время в IANA-зоне, повестка, до 200 участников; встреча создаётся до записи |
| `/meetings/:id` | Участники, повестка, загрузка аудио/видео, этап, ошибка и retry; защищённый аудиоплеер и транскрипт |
| Проверка в карточке встречи | Спикеры и предложения, many-to-one ручное сопоставление, неизвестные; саммари; добавление, правка, удаление поручений |
| Поручение в протоколе | Автор, исполнитель, срок, исходная формулировка срока, цитата, ссылки на реплики и переход к аудио; deep link `#task-ID` |
| Утверждение и экспорт | Явная отметка неполных данных, подтверждение публикации; DOCX/PDF с опциональным транскриптом, ошибки экспорта |
| `/tasks` | Только мои подтверждённые поручения, фильтры «В работе / Выполненные / Просроченные», изменение выполнения |
| `/notifications` | Тип события, прочитанные/непрочитанные, переход к объекту, отметка одного или всех прочитанными |

Дата создания встречи переводится в UTC именно из выбранной IANA-зоны, независимо от зоны браузера. Просрочка в UI берётся из backend-поля `overdue`; frontend не переопределяет серверный конец дня срока.

Отсутствующие исполнитель/срок/автор отмечаются как требующие уточнения. Ошибка извлечения имеет отдельное сообщение, не «поручений нет». Similarity и confidence показаны как числовые оценки без процентов «точности». Статусы `processing_status`, `approval_status`, `execution_status` разделены.

Микрофон доступен только в secure context (localhost или HTTPS) и при разрешении браузера. Поддерживаются выбранные браузером WebM/Opus, MP4 или Ogg; конвертация — на backend. Захват ограничен 60 секундами, дорожки останавливаются после записи и при уходе. Ожидание разрешения можно отменить; опоздавший поток сразу закрывается. Во время записи загрузка/удаление заблокированы. Физический микрофон пользователя автоматически не включался при проверке.

## Обновление: выдача доступа и собственный голос (контракт 1.1.0)

- В форме нового сотрудника добавлена опция «Создать учётную запись», логин и роль (по умолчанию employee). Сначала сохраняется сотрудник. Выдача аккаунта выполняется отдельно через `POST /users` без поля `password`. При ошибке карточка сотрудника остаётся, повтор отправляет только запрос создания аккаунта. Можно закрыть диалог, исправить логин в карточке и повторить выдачу.
- Диалог выдачи/сброса показывает логин и временный пароль один раз и позволяет скопировать их. Пароль хранится только в локальном состоянии смонтированного диалога, не попадает в роутер, URL, общий auth-state, хранилища или логи. Закрытие очищает это состояние; во время запроса закрытие заблокировано. После закрытия восстановить пароль можно только новым сбросом.
- Карточка сотрудника показывает наличие доступа, логин, активность и необходимость смены пароля через `GET /users` с пагинацией. Сброс `POST /users/{id}/reset-password` требует подтверждения отзыва сессий. Сброс собственного admin-аккаунта из UI отключён: отзыв текущей сессии мог бы закрыть одноразовый пароль до передачи. Для этого случая UI предлагает другого администратора; backend API остаётся неизменным.
- `must_change_password` после входа и `/auth/me`, а также `403 PASSWORD_CHANGE_REQUIRED` из общего API-слоя включают отдельный обязательный экран. Рабочая оболочка и polling в это время размонтированы. Можно сменить пароль или выйти; прямой переход на другой frontend URL не снимает ограничение.
- Смена использует `POST /auth/change-password` с `current_password` и `new_password`, минимум 10 символов, повтор пароля и проверка отличия от временного. Серверные `INVALID_CURRENT_PASSWORD` / `WEAK_PASSWORD` показываются пользователю. Новые cookie устанавливает backend, новый `csrf_token` немедленно заменяется в памяти. После смены открывается `/profile`.
- В пользовательском меню появился «Мой профиль»: `GET /employees/me`, ФИО, должность, департамент, логин и голос. Сотрудник может отложить регистрацию и продолжить работу; в профиле остаётся ненавязчивое приглашение.
- Голосовой редактор доступен только владельцу профиля. Администратору в чужой карточке объясняется, как выдать сотруднику доступ; запись чужого голоса своим микрофоном не предлагается. Серверные проверки доступа обязательны независимо от UI.
- Регистрация: объяснение назначения и согласие → короткий RU/KZ-текст для чтения 20–30 секунд → запись с таймером → остановка → локальное прослушивание → повтор или отправка. Также доступна загрузка файла. Успех показывается после ответа API. Ошибки качества дополняются советами: говорить дольше, проверить микрофон/тишину, уменьшить усиление. Неудачная замена не очищает существующий профиль.
- Blob URL предпрослушивания освобождается при смене файла и уходе со страницы. MediaRecorder и дорожки останавливаются; отказ в разрешении, отсутствие устройства, несовместимый формат, отмена ожидания разрешения и ошибки API отображаются без фиктивного успеха.

Проверки обновления: `typecheck`, `build`, 16 unit-тестов и 11 сценариев Playwright (включая прежние сценарии). Новые браузерные проверки: создание аккаунта с ролью employee, одноразовый диалог, отсутствие микрофона в чужой карточке, вход временным паролем, обязательный экран после reload, смена с ротацией CSRF, переход в профиль, отложенная регистрация, файл и предпрослушивание, успешная регистрация и reload, quality-error при замене с сохранением прежнего профиля, подтверждённый сброс, повтор создания аккаунта без повторного POST сотрудника, запрет микрофона с доступной загрузкой. Реальный MediaRecorder проверяется прежним тестом на синтетическом WebAudio-потоке. Скриншот без паролей: `frontend/test-results/onboarding-access.png`.

**С настоящим backend этот frontend-прогон не выполнен:** `127.0.0.1:8000/health` во время работы отклонял соединение. Все перечисленные браузерные результаты получены на контрактных фикстурах v1.1.0; новая авторизация и регистрация не объявляются проверенными в production. Пользователь передал успешные результаты backend-тестов, но они не заменяют интеграционный браузерный прогон. Нужен запуск backend и реальная проверка выдачи/сброса/смены пароля, cookie через прокси и голосового профиля на подготовленной модели. Новых неизвестных полей/endpoint’ов нет. Backend, AI и контракт не изменялись; это обновление не коммитилось и не отправлялось.

## Удаление сотрудника — архивирование

Реализовано по контракту из задания, без изменений backend, `docs/API_CONTRACT.md` и OpenAPI со стороны frontend:

- `api.deleteEmployee(id)` отправляет `DELETE /api/employees/{id}` **без тела**, с текущими cookie и `X-CSRF-Token`. Пустой `204 No Content` обрабатывается без попытки читать JSON; повторный 204 тоже считается успехом.
- `Employee.can_delete` — необязательный boolean для совместимости со старым API. Кнопка показывается только при `can_delete === true`, в строке и карточке. Отсутствующее поле означает запрет. Окончательную проверку права, запрета удаления себя и последнего администратора выполняет backend.
- Кнопка строки не открывает карточку. Диалог содержит ФИО и объяснение: сотрудник исчезнет из активного справочника и потеряет доступ, история встреч и поручений сохранится. Это архивирование, не уничтожение истории.
- Используется нативный модальный `<dialog>` с `aria-labelledby`, `aria-describedby`, начальным фокусом на «Отмена» и возвратом фокуса после закрытия. Escape отменяет действие до отправки; во время запроса кнопки и закрытие заблокированы. Дополнительная синхронная блокировка защищает от двух быстрых кликов.
- Строка не исчезает до успешного ответа. После 204 диалог закрывается, появляется сообщение и заново запрашивается активный список. Поиск и номер страницы хранятся в параметрах маршрута; при опустевшей последней странице выбирается последняя доступная предыдущая страница. Переход в карточку сохраняет адрес списка; удаление из карточки возвращает туда же.
- При 403, 409 (`SELF_DELETE_FORBIDDEN`, `LAST_ADMIN`), 500 и сетевой ошибке диалог остаётся открытым, сотрудник остаётся в списке, сообщение объясняет проблему и разрешён повтор. При 404 повтор удаления блокируется: в списке сразу запрашиваются актуальные данные, в карточке после закрытия сообщения пользователь возвращается в заново загруженный список. 404 не показывается как успешное удаление.

### Проверка без backend

Используется существующий Playwright fixture API (`frontend/tests/e2e/fixture-api.ts`). Отдельный runtime mock-режим не нужен: перехват запросов включается **только внутри тестового браузера**. Production bundle эти фикстуры не импортирует.

```bash
cd frontend
npm ci
# Один раз на этапе подготовки, если Chromium ещё не установлен:
npx playwright install chromium
# Только сценарии удаления, backend запускать не нужно:
npm run test:e2e -- employee-delete.spec.ts
# Видимый браузер или пошаговая проверка:
npm run test:e2e -- employee-delete.spec.ts --headed
npm run test:e2e -- employee-delete.spec.ts --debug
# Полный набор:
npm run typecheck
npm run test
npm run build
npm run test:e2e
```

Playwright сам запускает Vite на `127.0.0.1:5173`, либо использует уже запущенный сервер. В тестах добавлены только синтетические сотрудники. Fixture явно вычисляет `can_delete`: секретарь может удалить обычного сотрудника, но не администратора/секретаря; собственную карточку удалить нельзя; employee не получает удаления ни для кого. Для проверки совместимости есть `legacyEmployeeResponse`, намеренно исключающий поле. `state.deleteError` задаёт код/сообщение ошибки, `deleteDelayMs` — задержку; ни один из этих параметров не доступен production-приложению.

Mock DELETE архивирует запись (`active=false`), отключает связанный тестовый аккаунт и исключает ID из набора кандидатов идентификации; повтор отвечает 204. Объект сотрудника и история не уничтожаются. Активный список и `total` вычисляются заново. Это имитация согласованного API, а не доказательство серверного архивирования или работы голосовой модели.

Проверено: **16 новых браузерных сценариев удаления**, весь набор **27 Playwright-сценариев**, **17 unit-тестов**, typecheck и production build. Покрыты роли, старый ответ, отмена/Escape/фокус, пустой 204, повторный DELETE, отсутствие преждевременного удаления строки, задержка и повторный клик, 403/два вида 409/500, 404 в списке и карточке, повтор после ошибки, сохранение поиска, последняя строка страницы, возврат из карточки и пустой справочник. Unit-тест отдельно проверяет отсутствие тела DELETE, cookie/CSRF и отсутствие вызова JSON-парсера для 204. Скриншот: `frontend/test-results/employee-delete-dialog.png` (игнорируется git).

### Настоящий API

Для настоящего API запустите `npm run dev` без Playwright: все запросы пойдут через Vite `/api` → `http://127.0.0.1:8000`. Другой внутренний адрес задаётся `BACKEND_URL=http://... npm run dev`. В production действует существующий nginx proxy. Переключателя/fallback на mock при ошибке нет: недоступный backend показывает ошибку. Сервер со старым ответом без `can_delete` не покажет кнопки удаления.

**Интеграция удаления с настоящим backend в этом изменении не проверена.** Проверки завершены на фикстурах, без ожидания готовности backend. На реальном сервере отдельно подтвердить: отзыв сессий архивированного пользователя, невозможность нового входа, исключение голоса из идентификации и сохранность истории встреч/поручений. Коммит и push этого изменения не выполнялись.

## Запись совещания из карточки (23 сентября 2026)

В «Запись и обработка» переключитесь на «Записать сейчас». «В помещении»
использует микрофон; «Онлайн-встреча» предлагает системный выбор вкладки/экрана
со звуком и необязательное добавление своего микрофона. Сначала подготовьте
источник, проверьте индикатор звука, уведомите участников и нажмите «Начать
запись». Необязательная ссылка сохраняется отдельно и открывается в новой вкладке.
Загрузка готового файла сохранена как исходный режим.

`MeetingLiveRecorder` имеет собственные recorder, tracks, AudioContext и очередь;
регистрация голоса сотрудника не изменялась. Web Audio смешивает только аудио,
не подключая его к колонкам. Display stream удерживается до завершения, но
видео не отправляется. MIME выбирается по поддержке браузера, в запросах передаётся
фактический MIME MediaRecorder. Один recorder выдаёт части контейнера каждые
примерно 2 секунды; бинарные части больше серверного лимита разбиваются без
перестановки байтов. Последовательные PUT используют существующие cookie/CSRF.
Последний dataavailable и stop предшествуют завершению очереди ACK и POST finish.
Предварительный полный snapshot заменяет старый, опрашивается без пересечения
запросов; его ошибка не отменяет сохранение аудио. После done карточка обновляется.

При сбое нажмите «Повторить отправку»: неподтверждённые байты остаются в памяти.
409 с next_sequence позволяет повторить нужную часть; конфликт содержимого
показывается явно. Резервную запись можно скачать после остановки или ошибки.
Общий лимит накопленных аудиоданных — 128 МБ плюс последний полученный Blob:
при достижении запись останавливается контролируемо. Это память вкладки, не
постоянное хранилище; перезагрузка/закрытие может потерять неотправленное аудио.
Предупреждение beforeunload зависит от браузера; переходы по ссылкам интерфейса
также требуют подтверждения. Кнопка Back самого браузера может не показать
подтверждение SPA-перехода. Отмена требует подтверждения и ответа cancel.

### Проверка без backend

```sh
cd frontend
npm ci
npm run test:e2e -- live-recording.spec.ts
# Интерактивная проверка на тех же явно включённых фикстурах:
npm run test:e2e -- live-recording.spec.ts --headed --debug
npm run typecheck

```

Playwright подключает `tests/e2e/fixture-api.ts` через перехват `/api/**` только
в тестовом браузере. Фикстура показывает revision, изменение текста,
finalizing/done, сетевой сбой и недоступный preview. Обычный `npm run dev`
и production всегда используют настоящий API; автоматического mock fallback нет.
Чтобы проверить backend, откройте обычный браузер с dev-сервером (прокси /api)
либо production и войдите реальной учётной записью. Использован контракт из задания;
общие API-документы, backend и Compose не менялись этим frontend-заданием.

Автоматизация проверяет последовательность и ограничение размера чанков,
последний чанк до finish, повтор отправки, замену snapshot без дублей, неизвестного
спикера, отказ разрешения, display без аудио, смешивание, отмену и очистку tracks,
завершение при ended и выход со страницы. Отдельный тест использует настоящий
MediaRecorder Chromium с искусственным Web Audio источником. Это не проверка
физического микрофона или реального системного захвата экрана.

Нужен secure context (HTTPS или localhost), MediaRecorder, Web Audio и для
онлайн-режима getDisplayMedia. Наличие аудио в захвате зависит от браузера,
ОС и выбранного источника; рекомендуется выбирать вкладку со звуком. При
отсутствии audio track интерфейс предлагает повторить выбор или использовать
микрофон. Если браузер не поддерживает нужный формат, доступна загрузка файла.
Реальный backend live API, физический микрофон и системное окно выбора экрана
в этом прогоне не проверены; это оставшиеся интеграционные проверки.

Результаты итогового прогона: `typecheck` и production build успешны;
17 модульных и 34 браузерных теста прошли (7 новых для записи совещания).
Карточка с записью и казахским предварительным текстом визуально проверена
по скриншоту Chromium. В обычном браузере без перехвата запросов backend
вернул HTTP 500; интерфейс показал ошибку и повтор. Успешного интеграционного
прогона live API с настоящим backend нет. Коммиты и push не выполнялись.

В карточке встречи доступны язык (Авто/Русский/Қазақша) и профиль распознавания.
Перед началом записи или загрузкой изменения нужно сохранить через
PATCH /meetings/{id}/speech-settings. Во время записи/обработки поля заблокированы.
Готовый протокол не изменяется при смене настройки. Fixture API поддерживает этот
контракт; тест «язык и профиль сохраняются до начала записи» проверяет сохранение
и повторное открытие карточки.
