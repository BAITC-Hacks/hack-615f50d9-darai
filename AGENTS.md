# DARAI — правила разработки

## Цель и приоритет

Хакатонный прототип за 5 часов: CRM сотрудников и совещаний → запись → транскрипт RU/KZ/смешанной речи → диаризация → идентификация по голосу → поручения (кто, кому, что, срок) → проверка секретарём → саммари → DOCX/PDF → уведомления внутри CRM.

План и согласованные расширения API: `docs/DEVELOPMENT_PLAN.md`. Приоритет: работающий end-to-end сценарий > оформление > дополнительные функции. План не является утверждением о готовности функций.

## Жёсткие ограничения

- Никаких внешних облачных API в рантайме. Аудио, текст и голосовые векторы не покидают контур. Никакой телеметрии.
- Модели и все вложенные зависимости предварительно подготовлены локально. HF_TOKEN используется только при подготовке; секреты не коммитить.
- Целевой запуск подготовленного окружения: `docker compose up`. Загрузка весов и образов — отдельный документированный подготовительный шаг.
- Не подменять отсутствующие модели или ошибки распознавания фиктивным успешным результатом.

## Стек

| Слой | Технология |
| --- | --- |
| Backend | Python 3.11, FastAPI, uvicorn |
| ASR | faster-whisper large-v3, language=None, word timestamps |
| Диаризация | pyannote/speaker-diarization-3.1 |
| Голосовые векторы | pyannote/wespeaker-voxceleb-resnet34-LM; одна версия для регистрации и сопоставления |
| LLM | Локальная Ollama/vLLM, OpenAI-совместимый endpoint из LLM_BASE_URL, JSON |
| БД | PostgreSQL + pgvector |
| Frontend | React + Vite + TypeScript |
| Медиа и экспорт | FFmpeg, python-docx, LibreOffice headless для PDF |

Не использовать название облачного провайдера как основание для обращения к нему: совместимость endpoint означает только формат протокола. Конкретные версии пакетов фиксировать после проверки совместимости. Автоопределение языка не гарантирует качество смешанной речи — проверять на фикстурах.

## Пайплайн и правила идентификации

1. Файл → FFmpeg → WAV, 16 kHz, mono. Потоковая запись — последующий этап.
2. ASR с таймкодами слов → диаризация → выравнивание по максимальному пересечению интервалов. При отсутствии пересечения/неоднозначности сохранять признак неопределённости.
3. Для каждого говорящего брать чистые сегменты ≥1.5 с без одновременной речи. L2-нормировать векторы, усреднить, повторно нормировать результат.
4. Сравнивать cosine similarity только с приглашёнными сотрудниками, имеющими совместимый голосовой профиль. Венгерский алгоритм должен допускать отказ от назначения через фиктивные варианты «Неизвестный».
5. Начальные пороги: similarity ≥0.55 и отрыв от второго кандидата ≥0.08. Все пороги из env, калибруются на фикстурах. Это не вероятность и не гарантия точности. Если кандидат один, применять только порог similarity и проверки качества.
6. Не назначать второго по качеству кандидата только из-за взаимно-однозначного ограничения. Разделённые кластеры одного человека требуют ручной проверки; ручное сопоставление может быть many-to-one.
7. LLM получает список участников, дату/часовой пояс и контекст поручения минимум ±3 реплики; неоднозначные ссылки требуют более широкого контекста. Не придумывать ответственного или срок.
8. Секретарь исправляет спикеров и поручения, затем подтверждает результат. Только подтверждённые поручения создают уведомления исполнителям.

## Правила реализации

- Загружать модели один раз на старте процесса через lifespan/singleton, не в запросах. На MVP один процесс backend и одна тяжёлая задача одновременно.
- Пороги, пути моделей, HF_TOKEN, LLM_BASE_URL и настройки ресурсов — из env; несекретные дефолты в `.env.example`.
- LLM-ответ валидировать Pydantic, включая допустимые ID, даты и confidence в [0,1]. При невалидном ответе — один retry, затем пустой список и явный флаг ошибки извлечения; в логах только техническая ошибка, без содержимого совещания.
- Долгие операции через BackgroundTasks, вне event loop; processing|done|error сохранять в БД вместе с этапом. BackgroundTasks не является надёжной очередью: при рестарте прерванные задания помечать error и разрешать явный повтор.
- Не смешивать состояние обработки записи, утверждение протокола и исполнение поручения.
- Не менять API без синхронного обновления плана/README и фронта.
- После каждого модуля — минимальный содержательный тест; для аудиомодулей фикстура из `backend/tests/fixtures/`. Дополнительно один полный тест на реальных локальных моделях, отдельно от mock-тестов.
- Не добавлять тяжёлые зависимости без необходимости.
- Голосовая регистрация не является голосовым входом. Профиль сотрудника отделён от учётной записи.
- Проверять доступ на сервере. Пользователь не должен получать чужие встречи, записи, векторы или уведомления по подставленному ID.
- Не хранить чувствительные данные в git; не логировать аудио, текст, токены и векторы. Экспорт и статика не используют внешние шрифты/CDN.
