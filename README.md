# DARAI — ИИ-ассистент для протоколирования совещаний

DARAI — проект системы, которая преобразует запись совещания в транскрипт, краткое саммари и список поручений с ответственными и сроками. Решение предназначено для совещаний на русском, казахском и смешанном русско-казахском языке («шала-казахском»).

Ключевое ограничение проекта: аудио и текст должны обрабатываться внутри контура заказчика, без передачи во внешние облачные API.

> **Статус репозитория:** сейчас опубликован только README. Приложение, модели, конфигурация развёртывания и тестовые записи пока отсутствуют. Ниже описаны целевые возможности, предлагаемая архитектура и план проверки; их работоспособность ещё не подтверждена реализацией.

## Проблема и ценность

Ручное составление протокола занимает время секретаря и создаёт риск пропустить поручение, неверно указать ответственного или потерять срок. Руководителям приходится дополнительно восстанавливать договорённости и проверять исполнение.

DARAI призван сократить время подготовки протокола и сделать поручения проверяемыми: каждое извлечённое поручение должно быть связано с исходной репликой и её временем в записи. Перед утверждением секретарь проверяет результат и исправляет неточности.

## Пользователи и основной сценарий

| Пользователь | Задача |
| --- | --- |
| Секретарь | Подготовить запись, проверить распознавание и поручения, экспортировать протокол |
| Руководитель или куратор | Просмотреть итоги, ответственных и сроки, контролировать исполнение |
| Исполнитель | Получить подтверждённое поручение и видеть срок его выполнения |

Целевой сценарий прототипа:

1. Секретарь уведомляет участников о записи и транскрибации с помощью ИИ и загружает аудио- или видеозапись совещания.
2. Система локально выделяет аудиодорожку, распознаёт речь и разделяет реплики по говорящим.
3. Секретарь сопоставляет обозначения говорящих с участниками совещания.
4. Система формирует черновик саммари и извлекает поручения: суть, ответственный, срок и подтверждающая реплика.
5. Секретарь проверяет спорные места, уточняет участников и сроки, утверждает протокол.
6. Система экспортирует итоговый документ в PDF/DOCX.

В дальнейшем руководитель или куратор сможет получать напоминания о приближении срока и просрочке. Подключение бота к Teams, Zoom и Google Meet, а также работа с live-потоком рассматриваются как отдельные этапы развития. Для первого прототипа предлагается загрузка готовой записи.

## Обязательные возможности и текущий статус

| Требование кейса | Целевая реализация | Статус |
| --- | --- | --- |
| Распознавание речи | Локальная транскрибация записи с временными метками | Не реализовано |
| Русский язык | Распознавание и извлечение поручений на русском | Не проверено |
| Казахский язык | Распознавание и извлечение поручений на казахском | Не проверено |
| Смешанная речь | Обработка переключений языка внутри реплики | Не проверено |
| Диаризация | Разделение реплик по говорящим с ручным сопоставлением имён | Не реализовано |
| Извлечение поручений | Суть, ответственный, срок и ссылка на реплику | Не реализовано |
| Саммари | Краткое изложение тем, решений и открытых вопросов | Не реализовано |
| Экспорт | Формирование итогового протокола в PDF/DOCX | Не реализовано |
| Закрытый контур | Локальные модели, хранение и обработка данных | Архитектурное требование |

Диаризация отвечает на вопрос «какой говорящий произнёс реплику», но сама по себе не определяет имя человека. Кроме того, автор поручения и его исполнитель могут быть разными участниками. Ответственного необходимо определять по содержанию разговора и подтверждать при проверке протокола.

## Предлагаемая архитектура

```text
Веб-интерфейс секретаря
        |
        v
Локальный backend и очередь обработки
        |
        v
Извлечение аудио и подготовка записи
        |
        +--> Локальное распознавание речи --> Текст и временные метки
        |
        +--> Локальная диаризация ---------> Интервалы говорящих
        |                                       |
        +-------------------+-------------------+
                            v
              Транскрипт с метками говорящих
                            |
                            v
              Локальная языковая модель
              Саммари и извлечение поручений
                            |
                            v
              Проверка и утверждение секретарём
                            |
                            v
              Хранилище протоколов и поручений
                            |
                            v
                       PDF / DOCX
```

Все компоненты обработки должны работать внутри инфраструктуры заказчика. Для воспроизводимости будущая реализация должна фиксировать версии зависимостей, моделей, их весов и параметры запуска.

### Кандидаты на технологический стек

Это варианты для реализации, а не установленные зависимости репозитория. Окончательный выбор требует проверки лицензий, ресурсов и качества на тестовых записях.

| Компонент | Предлагаемый подход |
| --- | --- |
| Интерфейс | Веб-приложение для загрузки, просмотра транскрипта и редактирования поручений |
| Backend | Python / FastAPI для управления обработкой и экспорта |
| Подготовка аудио | FFmpeg для извлечения и преобразования аудиодорожки |
| Speech-to-text | Мультиязычная модель Whisper с локальным запуском, например через faster-whisper |
| Диаризация | Локальный pipeline на базе pyannote.audio с предварительно подготовленными весами |
| Анализ текста | Локальная мультиязычная LLM через llama.cpp или другой self-hosted runtime |
| Хранение | PostgreSQL для метаданных и поручений, локальное файловое хранилище для записей и документов |
| Экспорт | Генерация DOCX и PDF внутри контура |
| Развёртывание | Контейнеры с заранее подготовленными зависимостями и моделями |

Поддержку казахского языка и переключений между языками нельзя считать подтверждённой только на основании выбора мультиязычной модели. Её необходимо отдельно измерить на русских, казахских и смешанных записях.

## Входные и выходные данные

**Вход:** запись совещания, дата и часовой пояс встречи, список участников для сопоставления говорящих. Конкретные форматы, ограничения длительности и размера файла будут определены после реализации загрузки.

**Выход:**

- Транскрипт с временными метками и участниками.
- Саммари с основными темами, решениями и открытыми вопросами.
- Структурированный список поручений.
- Итоговый протокол в PDF/DOCX.

Предлагаемые поля поручения:

| Поле | Назначение |
| --- | --- |
| `description` | Что необходимо сделать |
| `assignee` | Ответственный участник; `null`, если его нельзя установить |
| `deadline` | Нормализованный срок; `null`, если он не указан или неоднозначен |
| `deadline_source` | Исходная формулировка срока из разговора |
| `source_speaker` | Кто произнёс подтверждающую реплику |
| `source_start`, `source_end` | Начало и конец фрагмента записи в секундах |
| `source_text` | Текст реплики для проверки |
| `needs_review` | Требуется ли уточнение секретарём |

Если ответственный или срок не названы, система должна помечать поле для уточнения. Относительные сроки вроде «завтра» следует вычислять относительно даты совещания и его часового пояса. Неоднозначные выражения необходимо сохранять в исходном виде до подтверждения человеком.

### Иллюстративный пример

Смоделированная реплика участника А:

> Дана, подготовь отчёт по бюджету до 25 сентября 2026 года.

Ожидаемое поручение:

| Суть | Ответственный | Срок | Источник |
| --- | --- | --- | --- |
| Подготовить отчёт по бюджету | Дана | 2026-09-25 | Реплика участника А |

Этот пример показывает ожидаемое поведение, а не результат работы существующей модели. Для оценки казахского и смешанной речи нужны отдельные примеры и эталонная разметка.

## Приватность и закрытый контур

Требования к будущей реализации:

- Не отправлять аудио, транскрипты, промпты и результаты во внешние облачные API.
- Подготовить веса моделей и зависимости заранее, чтобы обработка не требовала доступа к интернету.
- Отключить внешнюю телеметрию и проверить сетевую активность компонентов.
- Ограничить доступ к записям и протоколам согласно ролям пользователей.
- Защитить передачу и хранение данных, определить сроки хранения и порядок удаления, включая временные файлы.
- Не записывать содержимое совещаний в технические логи без обоснованной необходимости.
- Уведомлять участников о записи и обработке речи до начала совещания.
- Использовать синтетические или анонимизированные данные для демонстрации; не публиковать реальные записи, персональные данные и секреты в репозитории.

Размещение компонентов локально само по себе не подтверждает защищённость решения. Эти требования должны быть реализованы и проверены перед использованием реальных чувствительных данных.

## Запуск и воспроизводимость

**Запустить приложение из текущего репозитория пока нельзя:** исходный код, зависимости, веса моделей и конфигурация окружения не опубликованы. Команд установки и запуска на этом этапе нет.

Чтобы прототип можно было воспроизвести, вместе с реализацией необходимо добавить:

1. Поддерживаемые ОС и проверенную конфигурацию CPU/GPU, RAM и диска.
2. Зафиксированные зависимости, идентификаторы и версии моделей, инструкции получения весов и сведения об их лицензиях.
3. Пример конфигурации без секретов и команды запуска всех компонентов.
4. Порядок подготовки среды с доступом к интернету и последующего запуска в изолированном контуре.
5. Анонимизированную или синтетическую тестовую запись с эталонным транскриптом и поручениями.
6. Пошаговый демонстрационный сценарий и пример экспортированного протокола.
7. Результаты измерения качества и времени обработки на указанном оборудовании.

## План проверки прототипа

Для демонстрации предлагается подготовить записи на русском, казахском и смешанном языке с несколькими говорящими. Эталонная разметка должна включать реплики, участников, поручения, ответственных и сроки.

| Проверка | Ожидаемый результат |
| --- | --- |
| Запись на русском | Транскрипт и поручения сопоставимы с эталоном |
| Запись на казахском | Сохраняются смысл, имена участников и сроки |
| Смена языка внутри реплики | Поручение извлекается без потери смысла при переключении языка |
| Несколько говорящих | Реплики разделены и доступны для сопоставления с участниками |
| Руководитель поручает задачу другому участнику | Исполнителем указан адресат поручения |
| Ответственный или срок отсутствует | Поле не выдумано и помечено для уточнения |
| Относительный срок | Используется дата встречи, исходная формулировка сохранена |
| Исправление секретарём | Изменения отражены в итоговом протоколе |
| Экспорт | Документ открывается и корректно отображает кириллицу и казахские символы |
| Работа без внешней сети | Полный цикл обработки и экспорта выполняется локально |

Рекомендуемые метрики: WER/CER для распознавания, DER для диаризации, precision/recall извлечения поручений, точность определения ответственного и срока, время обработки и время ручной проверки. Результаты следует приводить отдельно для каждого языка и смешанной речи. Численные показатели качества в этом репозитории пока отсутствуют.

## План развития

1. **Базовый прототип:** загрузка записи, локальные ASR и диаризация, транскрипт с временными метками.
2. **Подготовка протокола:** локальное извлечение поручений и саммари, сопоставление участников, ручная проверка, PDF/DOCX.
3. **Контроль исполнения:** статусы «в работе / просрочено / выполнено», фильтры по ответственным, напоминания и рассылка утверждённых выдержек.
4. **Расширение входных каналов:** live-поток и подключение к платформам совещаний с отдельной проверкой совместимости с требованиями закрытого контура.
5. **Корпоративные интеграции:** СЭД, классификация поручений по срочности и направлению, голосовая идентификация при наличии необходимых оснований и согласий.

Полноценная интеграция с СЭД и промышленное развёртывание находятся за пределами обязательной части хакатона.
